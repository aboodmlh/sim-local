# Sim Local Parallel Worker

هذه النسخة تشغّل عمليات الشراء في جلسات مستقلة بالتوازي باستخدام `ThreadPoolExecutor`. بعد ظهور `403 Forbidden` عند تشغيل عدد كبير من الطلبات، أصبحت الإعدادات الافتراضية الآمنة **جلستين في الوقت نفسه** مع تأخير 8 ثوانٍ بين بدء المهام. يمكن تغييرها من متغيري `MAX_WORKERS` و`DELAY_BETWEEN_SUBMISSIONS` بعد التأكد أن مزود الخدمة يقبل معدل الطلبات.

## التشغيل على Railway

ارفع الملفات التالية إلى مستودع GitHub أو إلى مشروع Railway:

| الملف | الغرض |
|---|---|
| `main.py` | السكربت الرئيسي بالتوازي |
| `requirements.txt` | مكتبات Python المطلوبة |
| `emails.txt` | إيميل واحد في كل سطر |
|

في Railway، اجعل أمر التشغيل:

```bash
python main.py
```

ثم أضف المتغيرات التالية من قسم **Variables**:

```text
TELEGRAM_BOT_TOKEN=توكن_البوت
TELEGRAM_CHAT_ID=رقم_الشات
MAX_WORKERS=2
DELAY_BETWEEN_SUBMISSIONS=8
VOUCHER_CODE=EXPERTAFRICA
SKU=ESFX-1681-SL1
```

المتغيرات الاختيارية هي `DELAY_BETWEEN_SUBMISSIONS` لتأخير إرسال المهام الجديدة، و`CREATE_ORDER_RETRIES` و`CREATE_ORDER_BACKOFF` لإعادة المحاولة تدريجياً عند 403 أو 429 أو أخطاء الخادم، و`POLL_MAX_WAIT` و`POLL_INTERVAL` للتحكم في متابعة حالة الأوردر. لا ترفع `MAX_WORKERS` إلى 5 إلا بعد اختبار محدود؛ سجلاتك الحالية تشير إلى أن المعدل العالي يؤدي إلى رفض الطلبات.

> **تنبيه مهم:** لأن السكربت ينفذ عمليات شراء حقيقية، لا تضبط Railway على إعادة التشغيل المتكرر تلقائياً بعد انتهاء العملية؛ وإلا قد يعيد معالجة نفس ملف الإيميلات وينشئ طلبات مكررة. شغّله كـ Job/عملية يدوية أو استخدم قائمة إدخال جديدة بعد كل تشغيل.

## الفرق عن النسخة القديمة

النسخة القديمة كانت تنتظر انتهاء كل إيميل ثم تنفذ الإيميل التالي، بالإضافة إلى تأخير ثابت بين العمليات. النسخة الجديدة ترسل المهام إلى خمس جلسات مستقلة، وكل جلسة تظل مسؤولة عن أوردرها واستعلاماته، لذلك انتظار تجهيز شريحة واحدة لا يوقف بقية الإيميلات.

كل جلسة تستخدم `requests.Session` خاصة بها، ويتم تجميع النتائج عند اكتمال المهام. كما أُزيلت أسئلة `input()` لأن Railway لا يعمل عادةً بواجهة تفاعلية، وأصبح التوكن ورقم الشات ومتغيرات التشغيل تُقرأ من Railway Variables.
